Performances du moteur

Deux grandeurs, deux statuts. Le travail — le nombre d'instructions exécutées — est déterministe : il se compare d'une version du moteur à l'autre, et c'est de lui qu'on parle quand on dit qu'une évolution coûte ou rapporte. Le temps, lui, dépend de la machine, du compilateur et jusqu'à l'adresse à laquelle le code est placé : il ne vaut que comme relevé, à une date et sur un matériel donnés.

Chaque barre est un multiple du temps de référence : à gauche du repère, le langage est plus rapide ; à droite, plus lent. Les neuf tests portent chacun sur un chemin différent du moteur, et une somme de contrôle identique dans les trois langages garantit qu'ils font le même travail.

Méthode

Pourquoi deux instruments. Tous les gestionnaires d'opcodes de la machine virtuelle vivent dans une seule fonction (dispatch par computed-goto), si bien que modifier n'importe lequel déplace l'adresse de tous les autres et change le comportement du cache d'instructions. L'effet est mesuré à ±7 % : ajouter du code mort dans un gestionnaire que le test n'exécute jamais suffit à le rendre 7 % plus rapide. Un écart de quelques pour cent sur un temps ne dit donc rien d'un coût réel. Le compte d'instructions, lui, est indifférent à l'adresse du code comme au cache. Instructions en hausse : coût réel, à corriger. Instructions stables et temps qui bouge : placement, rien à optimiser — et figer une disposition favorable ne servirait à rien, le prochain changement la défera.

Le travail. Relevé par bash bench/icount.sh <réf> [<réf>], qui compile chaque version dans un espace de travail jetable et compte les instructions exécutées (callgrind). Un jalon par journée mesure l'état en fin de journée : l'écart affiché cumule tous les commits du jour, et le sujet indiqué — celui du dernier — n'en porte ni le mérite ni le blâme. Attribuer un écart à un commit précis demande de mesurer ce commit. Seules les journées touchant le cœur du moteur sont jalonnées ; ailleurs le compte est stable par construction. La borne basse n'est pas l'historique git mais le langage : avant le 20 juin 2026, ces trois scripts ne s'exécutent pas.

Le temps. Relevé par bash bench/bench_all.sh. Chaque test est lancé plusieurs fois et le meilleur temps est retenu, un run unique étant trop sensible à la contention du processeur. Les trois langages mesurent le temps processeur, non le temps écoulé. Aucun environnement n'est normatif : ni les temps ni les coefficients ne se transportent d'une machine ou d'une session à l'autre, et deux chiffres ne se comparent que mesurés dans la même série.
